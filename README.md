# WINC 規則・決定原本

会の規則・決定を、JSON Schema付きのJSON原本として管理します。Webアプリは原本の閲覧・作成・編集・差分確認を補助します。編集者はこのリポジトリをクローンし、変更をPRで提出します。mainへのマージで施行します。

申請・議論・議決・承認の機能は持ちません。議決日・機関・理由も記録しません。本文の履歴はGitが管理します。

## 起動する

Bun 1.4.2以降とGitが必要です。

```sh
bun install --frozen-lockfile
bun run dev
```

<http://127.0.0.1:3000/>を開きます。`PORT=3001 bun run dev`でポートを変更できます。サーバーはループバックにのみ接続し、`data/`のJSONを直接読み書きします。

文書一覧から閲覧・編集でき、「新規作成」から規則・決定を作成できます。第1項は条名に続けて表示し、第2項以降に項番号を付けます。章・条・項・号・附則を編集でき、単一文字列の決定・公示も扱えます。本文はプレーンテキストで、改行を保持します。

閲覧画面は左に変更履歴と目次、右に条文を表示し、それぞれ独立してスクロールします。目次の目のボタンで表示・非表示を切り替えられます。条文比較は変更後・変更前を同じ行に揃え、変更部分を黄色で示します。「変更箇所のみ」と前後の差分への移動も使えます。編集画面の構造操作は、入力中の条・項の近くに表示します。

## 編集してPRを作成する

```sh
git switch -c update-rules
# Web画面で編集し「原本に保存」、またはJSONを直接編集
git add data/
bun run commit -m '規則を改正する'
git push -u origin update-rules
```

その後GitHubでPRを作成します。コミット・push・PR作成はWeb画面では行いません。今回の再構築でGitHub認証やPR作成APIは削除しています。

`bun run commit`は、このコミットに限って`.githooks/pre-commit`を有効にします。UUIDのない新規要素にUUIDを付与し、ステージ済み原本を検証してからコミットします。通常の`git commit`でも有効にする場合は、クローンごとに次を実行してください。

```sh
bun run hooks:install
```

既存の`core.hooksPath`が別に設定されている場合は上書きせずに停止します。フックはステージ済みの原本だけを処理し、UUID未付与の原本が部分ステージされている場合は停止します。未ステージの変更を勝手にコミットへ含めません。Gitフックを使わないコミットでも、CIでUUID欠如・重複を検出します。

UIでは編集中の対応付け用にUUIDを先に確保し、その値をコミット後も使用します。手書き原本ではUUIDを省略しておき、コミット前処理で付与できます。一度コミットされたUUIDは変更しないでください。

## 原本の形式

現行形式は`schema/document.schema.json`で定義します。1文書1JSONで、ファイル名は文書IDと一致させます。

```json
{
  "$schema": "../schema/document.schema.json",
  "schemaVersion": 1,
  "id": "example-rules",
  "title": "利用規則",
  "kind": "運営規則",
  "status": "active",
  "body": {
    "articles": [
      {
        "name": "第一条",
        "caption": "目的",
        "paragraphs": [{ "text": "この規則は、利用について定める。" }]
      }
    ]
  }
}
```

上の例はコミット前のUUID未付与の状態です。`uuid`は文書・章・条・項・号・附則に付きます。旧原本の固定リンクは`anchor`で保持します。

条名は`第一条`、`第六条の二`等の名称として保存し、配列への挿入・削除・移動で自動変更しません。番号を変える場合は条名を編集するか、編集画面で明示的に再採番します。本文中の参照は自動変更しません。参照警告は確認の補助で、「前条」「同条」や他文書への参照の意味を保証しません。

決定・公示・その他文書では`body`を単一の文字列にできます。規則の本文は条文構造とします。条文形式は、章なしの`articles`または章ありの`chapters`のいずれかを持ちます。編・節・款、添付ファイル・別表は扱いません。附則の本文は扱いますが、制定・改正の記録を自動追加しません。

`status`は`active`（有効）か`repealed`（廃止）です。作業中・PR提出済み等の状態は原本へ保存しません。ローカルでは作業中の表示を付けます。

## 差分と履歴

比較元は既定で`HEAD`とローカル`main`のmerge-baseです。mainがなければ取得済み`origin/main`、それもなければHEADを使います。自動fetchは行いません。HEADとの比較にも切り替えられます。

差分は「Gitの比較元 → 編集中」を表示します。ファイルへ保存しても比較元を変更しないため、差分は残ります。未保存かどうかは「保存済み → 編集中」で別に判定します。UUIDで同じ条・項・号を追跡し、名称変更・移動・本文変更を分けて表示します。

変更履歴からGitの各版を選び、当時の本文や現在の本文との差分を表示できます。旧形式の版も読み込み時に変換します。過去の本文を、制定・施行日の一覧から推測して作ることはありません。ファイル改名の追跡は初期実装の対象外です。

保存時は構造・ID・名称等を検証し、読み込み後に他のエディタで原本が変更されていたら上書きせずに通知します。Undo/Redoは現在の編集セッション内で使えます。別プロセスとの同時共同編集は対象外です。

## 構成

```text
data/                  原本JSON
schema/                現行JSON Schema
src/domain/            編集・差分・参照・検証・保存形式
src/server/            Bunローカルサーバー、原本保存、Git読み取り
src/web/               React画面、共有条文描画、Tailwind・印刷CSS
src/generated/         スキーマから生成した型
scripts/               Bunで実行する検証・生成・移行・コミット補助
tests/unit/            原本・差分・保存API・コミット前処理
tests/browser/         実ブラウザによる閲覧・編集・保存・履歴
docs/                  設計
.githooks/             コミット前のUUID補完と検証
```

## 検証と公開

```sh
bun run generate       # スキーマから型生成
bun run validate       # 全原本とUUIDを検証
bun run check          # 生成型の整合性とTypeScriptの型チェック
bun run test           # 原本・差分・保存・Git処理のテスト
bun run build          # 閲覧専用の静的サイトをdist/へ生成
bun run verify         # CIと同じ検証・型チェック・テスト・ビルド
bunx --bun playwright install chromium
bun run test:browser   # 一時原本で実行。実データは変更しない
```

ブラウザテストでインストール済みのChromiumを使う場合は`LAW_CHROMIUM_PATH`に実行ファイルを指定できます。

公開先はGitHub Pagesを想定し、既定のbase pathは`/law/`です。`LAW_BASE_PATH=/ bun run build`で変更できます。文書ごとにHTMLを出力するため、直接アクセスでも本文を読めます。公開物には編集画面のコード・保存APIを含めません。`/edit/...`はローカル編集の案内です。履歴の公開には過去のGit情報が必要なので、CIでは`fetch-depth: 0`でチェックアウトします。

PRとmainで同じ原本検証・型チェック・テスト・ビルド・ブラウザテストを実行します。mainへのpushで公開します。GitHub側のPages設定・ブランチ保護は別途設定してください。mainへのマージが施行の基準で、公開ページはデプロイ完了後にその内容へ更新されます。

旧原本の移行は`bun run migrate`で明示実行します。現行会則はすでに移行済みです。旧形式の本文・固定リンクを保持し、UUIDと条名を補いました。旧形式にあった日付のみの制定・改正記録は原本から外し、過去のGit履歴に残しています。
